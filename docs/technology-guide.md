# Technology guide

Why each technology is used, what it was chosen over, and where it appears in the system.
Entries are added as technologies are introduced. Status is `planned` until a slice uses it.

## Entry format
**What** / **Why chosen** / **Alternatives** / **Where used** / **Trade-offs** / **Status**

---

## Python 3.12+
- **What:** the primary language for the API, workers and agent layer.
- **Why chosen:** the LLM provider SDKs and AI tooling ecosystem are Python-first; mature `asyncio`
  and static typing support suit an async orchestration engine.
- **Alternatives:** Go (excellent concurrency, smaller AI SDK ecosystem); TypeScript (strong for the
  frontend, weaker fit for the backend ecosystem we need).
- **Where used:** everywhere on the backend.
- **Trade-offs:** the GIL limits CPU-bound parallelism. The workload is I/O-bound (database, LLM
  calls), so `asyncio` is the right model.
- **Status:** in use (slice 1)

## uv
- **What:** dependency and virtual-environment manager with a lockfile.
- **Why chosen:** fast, reproducible installs from a lockfile, and a single tool for environments and dependencies.
- **Alternatives:** pip + venv (no lockfile by default); Poetry (mature but slower).
- **Where used:** local development, CI, container builds.
- **Trade-offs:** newer than pip and Poetry, so some tutorials still show the older tools.
- **Status:** in use (slice 1)

## FastAPI
- **What:** async web framework for the HTTP API.
- **Why chosen:** async-native, built-in request validation through Pydantic, automatic OpenAPI docs,
  and dependency injection that suits per-request database sessions and auth.
- **Alternatives:** Django (batteries included, heavier and sync-first); Flask (sync-first, fewer built-ins).
- **Where used:** `app/api/`, `app/main.py`.
- **Trade-offs:** fewer built-in features than Django (admin, auth); we add what we need deliberately.
- **Status:** in use (slice 1)

## Pydantic
- **What:** data validation and schema library.
- **Why chosen:** one validation layer for API requests and responses, configuration, and LLM structured
  outputs. Agent responses are validated against the same kind of schema, which is central to reliability.
- **Alternatives:** dataclasses (no validation); marshmallow (less integrated with FastAPI).
- **Where used:** `app/schemas/`, settings, agent output schemas (Phase 4).
- **Status:** in use (slice 1)

## SQLAlchemy 2.x (async) with asyncpg
- **What:** ORM and SQL toolkit, with `asyncpg` as the PostgreSQL driver.
- **Why chosen:** the API and workers run on `asyncio`, so database access must not block the event loop.
  SQLAlchemy supports row-level locking (`with_for_update(skip_locked=True)`), which the job queue relies on,
  and typed models.
- **Alternatives:** sync SQLAlchemy with threads (simpler, but mixes models); SQLModel (thin wrapper, less
  control); raw SQL (maximum control, more boilerplate).
- **Where used:** `app/models/`, `app/core/db.py`, `app/services/`. Version 2.1 (2.0-style API).
- **Trade-offs:** async sessions cannot lazy-load relationships implicitly, so loading strategy is explicit
  (`selectinload`, `joinedload`). This is a feature for predictable queries but needs care.
- **Status:** in use (slice 1)

## Alembic
- **What:** database migration tool.
- **Why chosen:** versioned, reviewable schema changes that can be applied in CI and production.
  Autogenerated migrations are reviewed by hand before commit.
- **Alternatives:** create-all at startup (no history or safe upgrades).
- **Where used:** `backend/migrations/`. Revisions use readable sequential IDs (`0001`, `0002`, ...).
  `alembic check` runs in tests and CI to catch models that drifted from the migrations.
- **Status:** in use (slice 1)

## PostgreSQL
- **What:** the relational database and source of truth for all workflow state.
- **Why chosen:** transactions, row-level locking, `FOR UPDATE SKIP LOCKED` for safe job claiming, and
  JSONB for flexible structured payloads. See ADR-0001.
- **Alternatives:** Redis-only state (fast, but weak durability and history); an external workflow engine.
- **Where used:** all persistent state, the job queue, events. PostgreSQL 17 in Compose and CI.
- **Trade-offs:** polling-based job claiming is simpler than a broker but needs tuning under load (Phase 8).
- **Status:** in use (slice 1)

## asyncio
- **What:** Python's cooperative concurrency framework.
- **Why chosen:** a workflow worker spends most of its time waiting on LLM and database calls. `asyncio`
  runs many such tasks cheaply in one process.
- **Alternatives:** threads (heavier, race-prone); multiprocessing (needed only for CPU-bound work).
- **Trade-offs:** CPU-bound or blocking calls stall the event loop, so they are kept out of async paths.
- **Status:** in use by the API (slice 1); workers from slice 2

## pytest and HTTPX
- **What:** test runner and an async HTTP client.
- **Why chosen:** fixtures keep database setup clean; HTTPX's async client exercises the FastAPI app
  in-process. Tests run against a real PostgreSQL because locking and concurrency behave differently on SQLite.
- **Alternatives:** unittest (more boilerplate); SQLite in tests (not representative).
- **Status:** in use (slice 1)

## ruff and mypy
- **What:** linter/formatter and static type checker.
- **Why chosen:** fast, consistent style and early detection of type errors, enforced in CI.
- **Where used:** configured in `backend/pyproject.toml`; mypy runs in `strict` mode over app, migrations and tests.
- **Status:** in use (slice 1)

## Docker Compose
- **What:** local multi-container environment.
- **Why chosen:** one command starts PostgreSQL (and later the worker, Redis and frontend) with the same
  versions everywhere.
- **Where used:** `docker-compose.yml` (PostgreSQL only for now; host port 5433 by default to avoid clashing
  with a locally installed PostgreSQL). Data lives in a named volume so it survives container restarts.
- **Status:** in use (slice 1)

## GitHub Actions
- **What:** CI.
- **Why chosen:** runs lint, type checks, tests and migration checks on every PR.
- **Where used:** `.github/workflows/ci.yml`: a PostgreSQL service container, then one Makefile target per
  step (install, lint, format check, type check, migrate, drift check, tests with a coverage gate). The
  `backend` job is a required status check on `main` (ADR-0006).
- **Trade-offs:** tied to GitHub. The steps are Makefile targets, so moving to another CI system means
  rewriting the wrapper, not the checks.
- **Status:** in use (slice 1; expanded in Phase 9)

## pydantic-settings
- **What:** loads typed configuration from environment variables and `.env` files into a Pydantic model.
- **Why chosen:** configuration is validated at startup (a malformed value fails immediately, not mid-request),
  and it shares the validation model already used for the API.
- **Alternatives:** `os.environ` lookups (untyped, scattered); python-dotenv alone (loads files, no validation).
- **Where used:** `app/core/config.py`. Reads the environment, then the repository-root `.env` shared with
  Docker Compose.
- **Status:** in use (slice 1)

## Uvicorn
- **What:** the ASGI server that runs the FastAPI application.
- **Why chosen:** the standard production-grade server for FastAPI, with auto-reload for development.
- **Alternatives:** Hypercorn (HTTP/2 and HTTP/3 support, less common); Gunicorn with Uvicorn workers (process
  management, revisited at deployment in Phase 9).
- **Where used:** `uv run uvicorn app.main:app`.
- **Status:** in use (slice 1)

## pytest-asyncio
- **What:** pytest plugin that runs `async def` tests and fixtures on an event loop.
- **Why chosen:** the application code is async, so tests await it directly instead of wrapping calls.
- **Alternatives:** AnyIO's pytest plugin (also supports Trio, which this project does not need).
- **Where used:** `backend/tests/` (`asyncio_mode = "auto"`, function-scoped event loops).
- **Trade-offs:** connections must not be shared across event loops, so engines are created per test (ADR-0005).
- **Status:** in use (slice 1)

## GNU Make
- **What:** a task runner; the `Makefile` at the repository root gives each developer task a short name.
- **Why chosen:** one command interface for people and for CI (`make check` runs what the pipeline runs),
  preinstalled on Linux and macOS, and familiar to most engineers.
- **Alternatives:** `just` or `poe` (clearer syntax, another tool to install); shell scripts (no shared
  help listing or target dependencies); documenting raw commands (CI and docs drift apart).
- **Where used:** `Makefile`; called by `.github/workflows/ci.yml`.
- **Trade-offs:** Make syntax is unforgiving (tabs, `$$` escaping), so targets are kept to one or two lines.
- **Status:** in use (slice 2)

## pytest-cov (coverage.py)
- **What:** measures which lines and branches of `app/` the tests execute.
- **Why chosen:** shows untested code paths and lets CI fail when coverage drops below a threshold (90%).
- **Alternatives:** no measurement (gaps go unnoticed); a 100% requirement (rewards tests written for the number).
- **Where used:** `make coverage`, configured under `[tool.coverage]` in `backend/pyproject.toml`.
  The `greenlet` concurrency setting is required because SQLAlchemy's async layer runs driver calls in greenlets.
- **Trade-offs:** executed is not the same as verified; a line can be covered by a test that asserts nothing
  about it. Coverage complements the failure-injection and constraint tests, it does not replace them.
- **Status:** in use (slice 2)

## Dependabot
- **What:** GitHub's dependency update service; opens pull requests when new versions are published.
- **Why chosen:** keeps dependencies and CI actions current with no manual tracking, and every update is
  verified by the full pipeline before it can merge.
- **Alternatives:** Renovate (more configurable, more setup); manual updates (tend not to happen).
- **Where used:** `.github/dependabot.yml`: monthly, one grouped PR for Python packages and one for GitHub Actions.
- **Trade-offs:** adds PRs to review; grouping and a monthly schedule keep that to two a month.
- **Status:** in use (slice 2)
