# ADR-0003: Initial data model for templates, runs and tasks

Status: accepted

## Context
Slice 1 introduces the first three tables: `workflow_templates`, `workflow_runs` and `tasks`.
Later slices add workers that claim and update tasks concurrently, retries, events and
multi-user access, so early choices about keys, status columns and relationships are hard to
change once data exists.

## Decision
1. **UUID primary keys**, generated by the application (`uuid4`). IDs are not enumerable, which
   limits insecure-direct-object-reference probing, and an ID can be known before the insert,
   which later supports idempotent creation.
2. **Status columns are `VARCHAR(32)` with a named `CHECK` constraint**, mapped from Python `StrEnum`s
   (`Enum(native_enum=False, create_constraint=True)`). The database rejects unknown states even if
   application code has a bug. Migrations write the CHECK constraints explicitly.
3. **A template's task graph is one JSONB document** (`definition`), validated by Pydantic on the way in:
   1–100 tasks, unique keys, dependencies that reference known tasks, no self-dependencies. A template is
   always read and written as a whole.
4. **A run's tasks are normalized rows** in `tasks`, unique on `(run_id, key)`. Workers will lock, claim and
   update tasks individually, which needs row-level locking rather than edits inside a JSON document.
5. **Referential actions:** deleting a run cascades to its tasks; deleting a template that has runs is
   rejected (`ON DELETE RESTRICT`) so execution history cannot be removed by accident.
6. **Timestamps** are `timestamptz` with database-side defaults (`now()`), so every writer shares one clock.
   Columns with defaults define both an ORM default and a server default, so plain-SQL inserts stay valid.
7. **Constraint naming convention** on the metadata (`pk_`, `uq_`, `fk_`, `ck_`, `ix_`), so migrations and
   error handling can refer to constraints by stable names.

Deferred: the run-level `task_dependencies` table and state-transition rules (slice 2), and lease and
retry columns (Phase 3).

## Alternatives considered
- **Integer or bigint identity keys:** smaller and index-friendly, but enumerable and only known after insert.
- **UUIDv7 keys:** time-ordered and better for index locality; Python's standard library gains `uuid7` only in
  3.14. Worth revisiting.
- **Native PostgreSQL `ENUM` types:** compact, but values cannot be removed and changes need `ALTER TYPE`,
  which complicates migrations. The space saving is negligible at this scale.
- **Normalized template tasks (a `template_tasks` table):** queryable per task, but adds joins for a document
  that is never updated piecemeal.
- **Cascading template deletes:** convenient, but silently destroys history.

## Consequences
- Constraint changes (for example a new status) need a migration that drops and re-creates the CHECK.
- JSONB template definitions rely on application-side validation for structure; the database only
  guarantees valid JSON.
- Templates with runs cannot be deleted; archiving will be needed if deletion becomes a requirement.
